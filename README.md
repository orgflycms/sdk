# sdk — контракт плагина flycms

Открытый репозиторий. Здесь всё, что нужно, чтобы написать плагин для
магазина на flycms: контракт `sdk.go`, пример `example/`, правила ниже.

## Как устроен плагин

Папка с Go-файлами одного пакета и функцией `Init(api sdk.API) error`.
Папка называется полным именем плагина `<пространство>.<имя>`, например
`vitams.promo`: пространство имён партнёр выбирает при регистрации в
кабинете, оно — префикс всех его плагинов. Пакет внутри назван коротким
именем: `package promo`. Ядро магазина читает папку интерпретатором при
старте и по кнопке «Перечитать» в разделе «Плагины» — компилировать и
перезапускать ничего не нужно.

Что даёт `sdk.API` — в [sdk.go](sdk.go), там комментарий к каждому методу.
Живой пример — [example/](example/): пункт меню и страница.

Плагину доступны этот пакет и часть стандартной библиотеки Go — список
ниже. Сторонних модулей нет: их некому скачать.

## Что доступно плагину

Плагин исполняется интерпретатором внутри процесса магазина и получает не
всю стандартную библиотеку, а явный список: пакет `sdk` и пакеты ниже, в
каждом — проверенные имена, а не всё подряд. Импорт другого пакета — ошибка
загрузки «пакет … запрещён в песочнице плагина»; имя, которого нет в
списке, — тоже ошибка загрузки. Обе видны в разделе «Плагины». Свои файлы
плагин импортирует только из своей папки.

```text
archive/zip  bufio  bytes  cmp  compress/flate  compress/gzip  compress/zlib
container/heap  container/list  container/ring  context
crypto  crypto/aes  crypto/cipher  crypto/ecdh  crypto/ecdsa  crypto/ed25519
crypto/elliptic  crypto/hmac  crypto/md5  crypto/rand  crypto/rsa  crypto/sha1
crypto/sha256  crypto/sha512  crypto/subtle  crypto/tls  crypto/x509
crypto/x509/pkix
encoding  encoding/asn1  encoding/base32  encoding/base64  encoding/binary  encoding/csv
encoding/hex  encoding/json  encoding/pem  encoding/xml
errors  fmt  hash  hash/adler32  hash/crc32  hash/crc64  hash/fnv  hash/maphash
html  html/template  image  image/color  image/draw  image/jpeg  image/png
io  math  math/big  math/bits  math/cmplx  math/rand/v2
mime  mime/multipart  mime/quotedprintable  net/http  net/mail  net/netip
net/textproto  net/url  path  regexp  slices  sort  strconv  strings
sync  sync/atomic  text/tabwriter  text/template  time  unicode
unicode/utf16  unicode/utf8
```

Интерпретатор знает таблицу стандартной библиотеки **Go 1.22**: функций,
появившихся в Go 1.23 и позже, у плагина нет. `go build` с `go 1.27` из
`go.mod` их пропустит — проверяйте плагин загрузкой в магазин.

`slices` и `cmp` исполняются из встроенных generic-исходников Yaegi.
Открыты только `slices.Contains`, `slices.Index`, `slices.Equal`,
`slices.Clone`, `cmp.Compare`, `cmp.Less`. Для `slices.Equal[[]int, int]` и
`slices.Clone[[]int, int]` нужны явные параметры типа. Остальные имена,
включая `Insert`, `Replace`, `Sort`, `SortFunc`, `Max` и `cmp.Or`, закрыты
при проверке исходника плагина: некоторые операции Yaegi дают неверный
результат без ошибки. Псевдонимы импорта поддерживаются; точечный импорт
этих двух пакетов запрещён. `maps` закрыт из-за ошибок Yaegi.

`text/template` работает только со строками и не экранирует XML: XML-фиды
собирайте через `encoding/xml`. `archive/zip` читает из `io.ReaderAt` и
пишет в `io.Writer`, без открытия файлов по имени. Распаковывайте содержимое
через `io.LimitReader`; перед декодированием картинки проверяйте размеры
через `image.DecodeConfig`. Память плагина отдельным пределом не ограничена.

Форму с файлом читайте потоково через `r.MultipartReader()` и
`NextPart`/`NextRawPart`, затем `io.LimitReader(part, предел)`: временные
файлы не создаются. Предел тела запроса админки остаётся 1 МиБ.
`unicode` даёт функции и константы без общих таблиц; `net/mail` только
разбирает письма и адреса. Для своего цвета используйте
`image.NewUniform(color.Black)`, для счётчиков — `sync/atomic` без unsafe.

Интерпретатор — не компилятор Go, у него есть свои ошибки. Известная
ловушка: **не присваивайте нескольким полям структуры одним оператором**
(`e.Status, e.Amount = sdk.PayPaid, amount(m)`) — Yaegi v0.16.1 может молча
оставить поле прежним. Пишите по одному присваиванию на строку.

### Чего нет и почему

- **Файлов, процессов, окружения**: `os` и его подпакеты, `os/exec`,
  `syscall`, `io/fs`, `io/ioutil`, `path/filepath`, `embed`, `archive/tar`,
  `database/sql` (база — через `api.DB()`). Плагин живёт в
  процессе магазина: через файлы ему достались бы ключи и настройки, через
  процессы — сервер целиком.
- **Сети, кроме клиента HTTP(S)**: `net`, `net/smtp`,
  `net/rpc`, `net/http/*` (`httptest`, `httputil`, `cookiejar`),
  `tls.Dial` и `tls.Listen`. Своих серверов и сокетов у плагина нет: адреса
  он получает через `api.Handle`.
- **Обхода интерпретатора**: `reflect`, `unsafe`, `runtime` и подпакеты,
  `plugin`, `go/*`, `debug/*`, `testing`, `expvar`.
- **Журнала**: `log` и `log/slog` закрыты, `fmt.Print*` пишет в никуда.
  Показать что-то владельцу можно на своей странице в админке.
- **Прочего, чего нет в списке**, даже безобидного: `maps`, `iter`,
  `math/rand` (есть `math/rand/v2`), `encoding/gob`, `image/gif`,
  `image/color/palette`. Пакет открывается только правкой ядра магазина.
- **Файловых методов и общих реестров**: `mime.TypeByExtension`,
  `ExtensionsByType`, `AddExtensionType`; `zip.OpenReader`, `ReadCloser`,
  пакетные `RegisterCompressor`/`RegisterDecompressor`; `multipart.ReadForm`,
  `Form`, `FileHeader`, `File`; `Request.ParseMultipartForm` и `FormFile`;
  `text/template.ParseFiles`, `ParseGlob`, `ParseFS` и одноимённые методы.
  Методы шаблонов `Clone`, `New`, `Lookup`, `Templates` возвращают ту же
  безопасную обёртку. У `zip.Reader` и `zip.Writer` собственные реестры доступны.
- **Общих изменяемых таблиц**: `unicode.Cyrillic`, `Categories`, `Scripts`,
  `TurkishCase` и прочих таблиц Unicode, `image.Black`, `White`, `Transparent`,
  `Opaque`, `image.RegisterFormat`, `xml.HTMLAutoClose`, `xml.HTMLEntity`,
  `asn1.NullBytes` (используйте `[]byte{5, 0}`), `http.ErrNotSupported`,
  `crc32.IEEETable`. `crc32.MakeTable` и `crc64.MakeTable` возвращают свои
  копии таблиц: их можно менять без влияния на ядро и другие плагины.
  `net/textproto` ограничен `CanonicalMIMEHeaderKey` и `MIMEHeader`;
  `atomic.Pointer`, функции для указателей и `Uintptr` закрыты.
- Внутри разрешённых пакетов убрано немногое: `crypto/rand.Reader` (есть
  `rand.Read`), `crypto.RegisterHash`, `time.LoadLocation` и `time.Local`
  (часовой пояс — `time.FixedZone`, `time.UTC` или
  `time.LoadLocationFromTZData` с данными в памяти), `x509.SystemCertPool`,
  `x509.SetFallbackRoots`, `x509.VerifyOptions`.

### Горутины и отложенные вызовы

Разрешены: оператор `go`, `time.AfterFunc`, `context.AfterFunc`,
`sync.WaitGroup` (с методом `Go`), каналы, мьютексы, `sync.Once`, таймеры.

«Перечитать» и удаление плагина отправляют его прежнюю копию в отставку.
Фоновую горутину этой копии магазин останавливает на первом вызове сети
(`http.Client`, `http.Get`…), базы (`api.DB()`) или `time.Sleep`: вызов
обрывает горутину, её отложенные функции выполняются. Так останавливаются
горутины, запущенные литералом `go func(...) { ... }(...)`, и функции,
отданные в `time.AfterFunc` и `context.AfterFunc`. Горутина, запущенная
как `go worker(x)` или через `sync.WaitGroup.Go`, а также цикл без сети,
базы и `time.Sleep` (ждёт канал, тикер, считает) живут до перезапуска
магазина — после «Перечитать» их станет две. Поэтому фоновый цикл пишите
литералом `go func() { ... }()` со `time.Sleep` между проходами. Запросы,
которые шли в момент «Перечитать», доигрывают как обычно.

> **Единственное слабое место.** Магазин ловит панику плагина в `Init`, в
> запросе, в корзине и в оплате — она стоит плагину ответа или скидки, не
> магазина. В горутине, которую запустил сам плагин, этой защиты нет:
> неперехваченная паника там останавливает **весь магазин**. Служба
> перезапустится, но запросы, которые шли в этот момент, оборвутся.
>
> Правило: первая строка каждой своей горутины и каждой функции, отданной
> в `AfterFunc`, — `defer` с `recover()`. Модерация маркетплейса это
> проверяет и возвращает плагин без него.

```go
go func() {
	defer func() {
		if r := recover(); r != nil {
			// записать в свою таблицу, показать на своей странице
		}
	}()
	sync(ctx) // работа горутины
}()

func worker(jobs <-chan Job) {
	defer func() { recover() }() // обязательно: см. ниже про `go worker(...)`
	for j := range jobs {
		handle(j)
	}
}
```

Ядро подстраховывает, где может: само перехватывает панику и пишет её в
журнал магазина, если горутина запущена литералом `go func(...) { ... }(...)`
или функция отдана в `time.AfterFunc`, `context.AfterFunc`,
`sync.WaitGroup.Go`. **Не перехватывает** запуск именованной функции или
метода — `go worker(jobs)`, `go c.loop()`: там спасает только ваш
`recover()`. Не полагайтесь на подстраховку — пишите `recover()` всегда.

Ни ядро, ни ваш `recover()` не спасают от того, что Go считает не паникой,
а фатальной ошибкой — магазин остановится: одновременная запись в `map` из
двух горутин (закрывайте `map` мьютексом), `Unlock` незапертого `Mutex` и
`RUnlock` незапертого `RWMutex` (даже без горутин, прямо в `Init`),
бесконечная рекурсия.
Значение из `recover()` печатайте через `fmt.Sprint(r)`: приведение
`r.(string)` или `r.(error)` в интерпретаторе не сработает.

### `net/http` — обёртка

Имена те же, набор урезан: только клиент и то, что нужно обработчику.

Есть: `http.Get`, `Head`, `Post`, `PostForm` (таймаут 30 секунд),
`NewRequest`, `NewRequestWithContext`; `http.Client` с полями `Transport`,
`CheckRedirect`, `Jar`, `Timeout` и методами `Do`, `Get`, `Head`, `Post`,
`PostForm`, `CloseIdleConnections`; `http.Transport` с полями
`TLSClientConfig`, `DisableKeepAlives`, `DisableCompression`,
`ForceAttemptHTTP2`, `MaxIdleConns`, `MaxIdleConnsPerHost`,
`MaxConnsPerHost`, `IdleConnTimeout`, `TLSHandshakeTimeout`,
`ExpectContinueTimeout`, `ResponseHeaderTimeout`, `MaxResponseHeaderBytes` и
методами `RoundTrip`, `CloseIdleConnections`; `Header`, `Cookie`,
`SetCookie`, `Error`, `Redirect`, `NotFound`, `MaxBytesReader`,
`StatusText`, `DetectContentType`, константы методов и статусов.

Нет из привычного:

- серверной стороны: `ListenAndServe*`, `Serve*`, `Server`, `ServeMux`,
  `NewServeMux`, `Handle`, `HandleFunc`, `Handler`, `StripPrefix`,
  `TimeoutHandler`, `MaxBytesHandler`, `RedirectHandler`,
  `NotFoundHandler`. Адреса — только `api.Handle` с `http.HandlerFunc`;
- файлов: `FileServer`, `ServeFile`, `ServeContent`, `Dir`, `FS`,
  `NewFileTransport`; файлов из формы: `FormFile`, `ParseMultipartForm`,
  `MultipartReader`, поля `MultipartForm`. `FormValue` и `PostFormValue`
  читают только строку запроса и `application/x-www-form-urlencoded`;
- сырых соединений: `Hijacker`, `ResponseController`, `Pusher`, у
  `Transport` — `Proxy`, `DialContext` и остальных `Dial*`;
- глобальных объектов: `DefaultClient`, `DefaultTransport`,
  `DefaultServeMux`, `ProxyFromEnvironment`; своего `RoundTripper` в
  `Client` не подставить;
- разбора и записи потока: `ReadRequest`, `ReadResponse`, `Request.Write`,
  `Response.Write`.

Поля `Transport` задаются до первого запроса: позже их изменения не
действуют. Тело исходящего запроса читается в память целиком до отправки —
потоковой выгрузки нет. `http.Request` — та же обёртка: поля метода,
адреса, заголовков, тела и форм, `Host`, `RemoteAddr`, `TLS`; методы
`Context`, `WithContext`, `Clone`, `Cookie`, `Cookies`, `AddCookie`,
`UserAgent`, `Referer`, `BasicAuth`, `SetBasicAuth`, `PathValue`,
`SetPathValue`, `ParseForm`, `FormValue`, `PostFormValue`. У ответа — поля
`Status`, `StatusCode`, `Header`, `Body` и прочие, методы `Cookies` и
`Location`.

HTTPS со своим корневым сертификатом: `x509.NewCertPool()` →
`AppendCertsFromPEM` (или `AddCert`) → `&tls.Config{RootCAs: pool}` →
`&http.Transport{TLSClientConfig: cfg}`. Клиентский сертификат —
`tls.X509KeyPair` из PEM в памяти, в `Certificates`. В `tls.Config` только
данные: `RootCAs`, `ClientCAs`, `Certificates`, `ServerName`, `NextProtos`,
`InsecureSkipVerify`, `MinVersion`, `MaxVersion`, `CipherSuites`,
`CurvePreferences`, `SessionTicketsDisabled`, `Renegotiation`; колбэков
(`VerifyPeerCertificate`, `GetClientCertificate` и других), `Rand`, `Time`
и `ClientSessionCache` нет. У пула корней — `AppendCertsFromPEM`,
`AddCert`, `Clone`, `Equal`, `Subjects`, без `AddCertWithConstraint`. Нет
`tls.LoadX509KeyPair` и `NewLRUClientSessionCache`.

Контексты — `context.Background`, `context.TODO`, контекст запроса
(`r.Context()`), контексты перехватчика корзины и обработчика оплаты и то,
что из них сделали `context.With*`. Своя реализация `context.Context` не принимается:
`context.With*`, `NewRequestWithContext`, `WithContext`, `Clone` и
`api.DB()` на ней паникуют. Почему: стандартная библиотека зовёт методы
контекста в своих горутинах, и паника там уронила бы магазин.

### `html/template` — обёртка

Шаблоны — только из строк в памяти: `template.New`, `Must`, у шаблона
`Parse`, `Funcs`, `Delims`, `Option`, `New`, `Lookup`, `Templates`, `Clone`,
`Name`, `DefinedTemplates`, `Execute`, `ExecuteTemplate`; типы `HTML`,
`CSS`, `JS`, `URL` и другие, `FuncMap`, функции экранирования. Нет
`ParseFiles`, `ParseGlob`, `ParseFS` — ни у пакета, ни у шаблона, — а также
`AddParseTree`, поля `Tree` и констант `Err*`. Шаблон держите в коде
строкой: `embed` тоже закрыт.

## Разметка страниц плагина и CSP

Страницы плагина в админке (`/admin/x/<плагин>/…`) отдаются с той же
строгой политикой, что и весь магазин: `script-src 'self'; style-src
'self'; img-src 'self' data:; connect-src 'self'`. Исключений для плагинов
нет. Поэтому в разметке, которую плагин передаёт в `api.Page`:

- нет `<script>…</script>` и `<script src>` — ни с чужих адресов, ни со
  своих: скрипт плагина в админке не исполняется вовсе (см. «Ответы
  плагина» ниже);
- нет обработчиков в атрибутах (`onclick=`, `onsubmit=`…) — они не
  сработают;
- нет `style="…"` и `<style>` — оформляйте классами админки (`card`,
  `btn`, `btn-danger`, `input`, `field`, `label`, `data-table`,
  `notice`…);
- картинки — только со своего магазина или `data:`; запросы из браузера —
  только на свой магазин.

### Ответы плагина

Обработчик, зарегистрированный через `api.Handle`, пишет ответ не напрямую,
а через ядро. Страницы плагина открываются в админке под сессией
владельца, поэтому:

- **Заголовки безопасности — всегда ядра.** `Content-Security-Policy`,
  `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и
  `Strict-Transport-Security`, которые поставил или убрал плагин, в ответ
  не попадают: уходят значения ядра. `Content-Security-Policy-Report-Only`
  отбрасывается.
- **Куки ядра плагин не ставит.** `Set-Cookie` с именами `flycms_…` и
  `cart` отбрасывается (в журнале магазина — предупреждение). Свои куки с
  другими именами — можно.
- **Тип ответа — из списка:** `text/html` (страницы — через `api.Page`),
  `application/json`, `text/plain`, `text/csv`, `application/pdf`,
  `image/png`, `image/jpeg`, `image/gif`, `image/webp`. Любой другой
  `Content-Type` — JavaScript (`text/javascript`, `application/javascript`),
  SVG, XML, `application/octet-stream` — ядро заменяет ответом 500 с
  объяснением, тело плагина не отдаётся. Не назвали тип — ядро определит
  его по первым байтам (`http.DetectContentType`) и проверит по тому же
  списку. Все ответы идут с `X-Content-Type-Options: nosniff`.
- Ответ без тела (`204`, перенаправление `http.Redirect`) проходит как
  есть; остальные заголовки (`Content-Disposition`, `Cache-Control`,
  `Location`) плагин ставит сам.
- **Заголовки проверяются без учёта регистра.** `w.Header()` — карта
  плагина: ядро переносит её в ответ при первом байте тела, приводя имена
  к обычному виду, так что `h["set-cookie"]` проверяется так же, как
  `Set-Cookie`. `Clear-Site-Data` и `Trailer` не уходят никогда; правки
  карты после первого байта в ответ не попадают; два разных
  `Content-Type` — ответ 500, повтор `Location`, `Content-Length`,
  `Content-Encoding`, `Content-Disposition` отбрасывается.
- **`Flush` до первого байта без `Content-Type` ничего не отправляет**:
  тип иначе назначил бы сервер по телу в обход списка. Потоковый ответ —
  сначала `Content-Type`, потом `Flush`.

Следствие: своего JavaScript у плагина в админке нет — ни встроенного, ни
файлом с адреса плагина. Векторную картинку отдавайте как PNG.

Что доступно без своего скрипта: подтверждение перед отправкой — атрибут
`data-confirm="Удалить?"` на кнопке; кликабельная строка таблицы —
`data-href="/admin/x/…"` на `<tr>`. Всё остальное делается обычными
формами и ссылками: страница плагина — серверная разметка.

## Открытые адреса

`api.HandlePublic(pattern, h)` — адрес без входа в админку: обмен с 1С
(CommerceML), вебхуки CRM, фиды маркетплейсов. Живёт под
`/x/<имя плагина>/…`, шаблон — как у `api.Handle`:
`api.HandlePublic("POST /exchange", …)` отвечает на
`https://shop.ru/x/vitams.onec/exchange`. Полный адрес для владельца
(вписать в 1С или CRM) даёт `api.PublicURL("/exchange")`: «Адрес магазина»
из настроек плюс путь; пока он не задан — только путь. Зовите его при
показе страницы, а не в `Init`: владелец мог задать адрес позже. Адрес
`/x/…` — контракт: вписанный в 1С не меняется.

**Кто вызывает — проверяет плагин**: пароль, подпись вебхука, Basic. Ядро
пускает всех, но держит то, что плагину не под силу:

- **Куки** до плагина не доходят (заголовок `Cookie` удалён), `Set-Cookie`
  ответа выбрасывается целиком: машинным клиентам куки не нужны, а сессии
  владельца и покупателей на источнике магазина плагину видеть незачем.
- **Тело — до 8 МиБ**, ядро читает его целиком до плагина: больше — `413`
  без вызова плагина, так что обрезанной выгрузки плагин не увидит. 1С
  режет файл частями по `file_limit`, который плагин отвечает на
  `mode=init` (до `8388608`).
- **Частота — 120 запросов в минуту** с одного адреса на плагин (дальше
  `429` с `Retry-After: 60`); **одновременно — 4 запроса** на плагин
  (пятый — `503` сразу). Места держатся, пока обработчик не вернулся, и
  «Перечитать» их не обнуляет.
- **Срок — 60 с** с начала запроса: контекст `r.Context()` отменяется,
  вызовы сети и базы прерываются. Обработчик ядро не снимает — сам следите
  за `ctx.Done()` в длинных циклах, иначе он занимает одно из четырёх мест.
- **Изменяющий запрос (POST, PUT, DELETE…) со страницы чужого сайта —
  `403`**: браузер сам приложил бы сохранённую Basic-авторизацию. 1С,
  CRM и curl заголовков `Origin`/`Sec-Fetch-Site` не шлют — их это не
  касается. GET каталога не меняет: так и пишите обработчики.
- **Ответ — данные:** `text/plain`, `application/json`, `application/xml`,
  `text/xml`, `text/csv`, `application/pdf`, `image/png|jpeg|gif|webp`.
  HTML, JavaScript, SVG и прочее — `500`, тело плагина не отдаётся: на
  источнике витрины это готовая площадка для подмены страниц. Заголовки
  безопасности — ядра, `Content-Security-Policy: default-src 'none';
  frame-ancestors 'none'; sandbox`, `Location` и `Refresh` выбрасываются
  (перенаправлений нет), остальные правила — как в «Ответы плагина».
- Плагин не загрузился или открытых адресов у него нет — `404`. Паника в
  обработчике — `500` и запись в журнал магазина.

Пример: обмен с 1С с Basic-авторизацией. Логин и пароль — настройки
плагина на его странице; сравнение — за постоянное время; адрес — только
по `https://`.

```go

```

## Оплата

Онлайн-оплату в магазине принимают только плагины: ядро умеет ручные
способы (наличные, перевод по реквизитам), а всё, что ходит к банку или
печатает счёт, — обработчик плагина. Он регистрируется в `Init`:

```go
func Init(api sdk.API) error {
	api.RegisterPayment("card", sdk.PaymentHandler{
		Title:  "Т-Банк: карта и СБП",
		Button: "Оплатить картой",
		Settings: []sdk.Field{
			{Key: "terminal_key", Label: "Ключ терминала", Required: true},
			{Key: "password", Label: "Пароль терминала", Kind: "password", Required: true},
		},
		Start:  start,
		Notify: notify,
		Check:  check,
	})
	return nil
}
```

Владелец заводит в админке способ оплаты, выбирает в списке «Обработчик»
`<плагин>/<код>` (`vitams.tbank/card`) и заполняет вкладку «Настройки» —
форма собирается из `Settings`. Способов с одним обработчиком может быть
несколько (два терминала), у каждого свои настройки. Покупатель видит
способ в оформлении, только если плагин загружен, все `Required`-поля
заполнены и в настройках магазина задан «Адрес магазина»: без него
некуда вернуть покупателя и некуда слать уведомление.

### Как идёт платёж

1. Заказ оформлен — у него оплата `pending` на сумму заказа.
2. Страница «спасибо», письмо о заказе и кабинет покупателя показывают
   кнопку с надписью `Button` (пусто — «Оплатить»), пока оплата `pending`
   или `failed` и заказ не оплачен целиком. Кнопка — ссылка
   `GET /pay/{payment_id}?token=…`. Владелец отметил оплату сам — кнопки
   нет, а `/pay` ждущей оплаты `Start` не вызывает.
3. По ссылке ядро собирает `sdk.Payment` и зовёт `Start`. Вызовы `Start`
   одной оплаты идут по очереди: двойной клик не создаст у провайдера два
   платежа — второй вызов увидит `ExternalID` первого.
4. Непустой `PayStart.ExternalID` ядро запоминает вместе с `URL`
   (`Payment.ExternalURL`), оплата `failed` снова становится `pending`.
   Дальше: есть `File` — покупатель получает файл; иначе есть `URL`
   (`https` или `http`) — переход к провайдеру; иначе — обратно на
   страницу заказа.
5. Провайдер шлёт уведомление на `Payment.NotifyURL` → `Notify` →
   `PayEvent` → ядро меняет статус.
6. Где уведомлений нет или они потерялись — `Check` (расписание ниже) →
   тот же `PayEvent`.

Статус оплаты и заказа меняет только ядро: сверяет сумму, пересчитывает
оплаченное, переводит заказ «Новый» → «Оплачен», пишет историю и шлёт
покупателю письмо о смене статуса. Обработчик только сообщает, что ответил
провайдер.

### Start

- Обязателен. Зовётся для любой неотменённой оплаты, в том числе
  оплаченной: счёт нужен и после оплаты, а карточному обработчику на
  оплаченную достаточно вернуть пустой `PayStart`.
- Ссылку открывают сколько угодно раз: письмо, кабинет, «назад» в
  браузере. Есть `ExternalID` и платёж у провайдера жив — верните тот же
  `{ExternalID, URL}`. Новый платёж — только когда старый окончательно
  отклонён или истёк: иначе старый оплатят после смены номера, и ядро его
  не найдёт.
- Ошибка показывается покупателю как есть («Для счёта нужен ИНН
  плательщика») — пишите её для покупателя, без кодов и стеков. Ответ —
  502 и запись в лог магазина.
- Ошибка вместе с `ExternalID` — номер всё равно запоминается: платёж у
  провайдера уже создан (счёт выставлен, а PDF не скачался), повторный
  `Start` не должен создать второй.
- Срок ядро держит само, даже если функция не слушает контекст. Не
  вернулась за 20 с — покупатель видит «Оплата временно недоступна…», а
  вызов доигрывает. Оплата занята, пока он не вернётся: его `ExternalID`
  ядро сохранит, и следующий `Start` его увидит. Больше 8 вызовов
  плагина, переживших срок, — его обработчики сразу отвечают ошибкой, пока
  зависшие не вернутся. Ответы `Notify` и `Check` после срока
  отбрасываются: провайдер повторит, опрос спросит в следующий раз.

### Notify и адрес уведомлений

Адрес — `POST /pay/notify/{method_id}`, где `method_id` — номер способа
оплаты в магазине. Он виден на вкладке «Настройки» способа (для
провайдеров, где адрес вписывают в личном кабинете) и приходит в
`Payment.NotifyURL` (для тех, кто принимает его в каждом платеже). Адрес не
секрет — защита в подписи.

- Подпись проверяет обработчик: `Notice.Settings` — настройки ровно того
  способа, на адрес которого пришло уведомление. Без проверки любой
  посторонний отметит заказ оплаченным. Подписи сравнивайте
  `subtle.ConstantTimeCompare`.
- Принимается только `POST`, тело — до 64 КиБ; куки и CSRF не нужны.
- Ошибка `Notify` — ответ 400, ничего не меняется.
- Оплату ядро ищет по `PayEvent.ExternalID` только среди оплат этого
  способа: даже верно подписанное событие не дотянется до чужого способа.
  Неизвестный номер — запись в лог и 200 с `Reply`, чтобы провайдер не
  повторял вечно.
- Оплату ядро ищет и по прежним номерам этой оплаты (`Start` вернул
  новый номер после отказа). По прежнему номеру засчитывается только
  `PayPaid`; `PayFailed` и `PayPending` о старой попытке ничего не меняют.
  У оплаченной оплаты номер больше не меняется.
- Способа нет или у обработчика нет `Notify` — 404; плагин сейчас не
  загружен (сломан, идёт «Перечитать») — 503, провайдер повторит позже;
  ошибка базы — 500, тоже повтор.
- `Reply` — тело ответа провайдеру (Т-Банк ждёт `OK`); пусто — 200 без
  тела.

### Check

Ядро само спрашивает провайдера о неоплаченных оплатах с `ExternalID` у
обработчиков с `Check`: первый час — раз в 5 минут, первые сутки — раз в
час, потом — раз в 6 часов, не дольше 30 дней. Ещё — когда покупатель
вернулся на страницу заказа (не чаще раза в 10 секунд) и по кнопке
владельца «Проверить оплату». Нет таких оплат — нет ни одного запроса.
`PayEvent.ExternalID` в `Check` можно не заполнять: оплата известна.

### Статусы

`Payment.Status` и `PayEvent.Status` — `sdk.PayPending`, `sdk.PayPaid`,
`sdk.PayFailed`. Ещё оплату может отменить владелец — отменённую ядро
обработчику не отдаёт. Переходы по событию:

| Сейчас | Событие | Итог |
|---|---|---|
| `pending`, `failed` | `paid`, `Amount` равен сумме оплаты | `paid`, заказ пересчитан |
| `pending`, `failed` | `paid`, сумма другая или 0 | статус прежний; в примечании оплаты «Провайдер подтвердил 1 000 ₽ вместо 2 364 ₽ — оплата не отмечена»; запись в лог |
| `pending`, `failed`, заказ отменён | `paid`, сумма верна | `paid`; статус заказа прежний; в примечании оплаты и в истории заказа «Получена оплата по отменённому заказу — верните деньги покупателю или восстановите заказ», письмо владельцу |
| `paid` | `paid` по тому же номеру платежа | ничего (повтор) |
| `paid` | `paid` по другому номеру той же оплаты (покупатель оплатил и прежнюю, и новую попытку) | статус прежний; деньги записаны заказу второй оплатой, заказ переплачен; в примечании оплаты и в истории заказа «Покупатель оплатил заказ дважды — верните лишнее покупателю и внесите возврат отрицательной суммой», письмо владельцу, предупреждение на сводке до возврата; повтор этого события — ничего |
| `pending` | `failed` | `failed`: покупатель может нажать кнопку ещё раз |
| `paid` | `failed`, `pending` | статус прежний; слово провайдера (`REFUNDED`) — в карточке заказа и строкой в примечании |
| отменена | любое | статус прежний; строка в примечании, для `paid` — запись в лог |
| любое | `pending` | запоминается только `ExternalStatus` |
| любое | не `paid` по прежнему номеру | ничего |

Примечание дописывается только при смене `ExternalStatus`: повтор
уведомления не плодит строк. Частичной оплаты одним событием нет — сумма
сверяется на равенство. Возврата из админки пока нет: его делают в
кабинете банка, слово провайдера видно в заказе, отрицательную оплату
владелец вносит руками.

### Что в Payment

- `Items` — строки заказа (комплект — одной строкой) и строка доставки,
  если она платная (`Delivery: true`, `Qty: 1`). Скидка заказа уже
  разнесена по строкам товаров: сумма `Sum` всех строк до копейки равна
  `Amount`, поэтому чек 54-ФЗ и счёт сходятся без пересчёта в плагине.
  Оплату на другую сумму завёл владелец — одна строка «Оплата заказа №N».
- `Payer` — поля формы оформления по их ролям: имя, почта, телефон,
  организация, ИНН, КПП, адрес доставки; `Type` — код типа плательщика;
  `Values` — все поля формы по коду, текстом. Юридического адреса среди
  ролей нет: берите его из `Values`, а код поля спрашивайте в настройках.
- `Created` — дата оформления в поясе магазина (Москва, UTC+3): в нём
  же даты показывает админка и кабинет покупателя. У плагина `time.Local`
  нет, а дата счёта нужна та, что видит владелец: `Created.Day()` и
  `Created.AddDate(…)` уже считают в этом поясе, «сегодня» —
  `time.Now().In(p.Created.Location())`.
- `ReturnURL` — страница заказа покупателя; `NotifyURL` — адрес
  уведомлений этого способа, пуст без `Notify`.
- `Settings` — настройки способа, к которому относится оплата, секреты
  тоже. Другим обработчикам и другим плагинам их не видно.

Своя база обработчику обычно не нужна: номер платежа, адрес формы или PDF
и слово провайдера ядро хранит само (`ExternalID`, `ExternalURL`,
`ExternalStatus`). Сырых тел уведомлений и ответов ядро не хранит.

### Настройки способа

`Field.Kind`: `""` — строка, `number`, `textarea`, `select` (варианты в
`Options`, без них плагин не загрузится), `password` — значение в форму не
выводится, пустое поле при сохранении его не меняет, очистка — флажком.
Пустое `Required`-поле прячет способ от покупателя, а владелец видит
предупреждение на вкладке. Ключи, которых нет в `Settings`, владелец
задаёт в таблице «ключ — значение» под формой: так держат служебные
ключи вроде адреса песочницы провайдера для тестов (`api_url`) — в форме
их нет, а обработчик читает их из `Settings` как обычные.

Функции обработчика зовутся параллельно: из запросов покупателей,
уведомлений и фоновой задачи. Общее состояние в переменных пакета берегите
мьютексом. Паника стоит одного вызова: покупатель увидит ошибку, магазин
работает. Контекст ограничен: `Start` — 20 с, `Notify` — 10 с, `Check` —
15 с; передавайте его в `http.NewRequestWithContext`.

## Доставка

Цену и срок доставки считает обработчик плагина (СДЭК, Почта России), а в
заказ её пишет ядро. Обработчик регистрируется в `Init` (с v0.4.0):

```go
func Init(api sdk.API) error {
	api.RegisterDelivery("door", sdk.DeliveryHandler{
		Title: "СДЭК: до двери",
		Settings: []sdk.Field{
			{Key: "account", Label: "Аккаунт", Required: true},
			{Key: "secret", Label: "Секретный ключ", Kind: "password", Required: true},
		},
		Quote: quote,
	})
	return nil
}

func quote(ctx context.Context, r *sdk.DeliveryRequest) (sdk.DeliveryQuote, error) {
	if r.Place.ID == 0 {
		return sdk.DeliveryQuote{Missing: "Укажите город"}, nil
	}
	// запрос к перевозчику с r.Settings["account"], r.Items, r.Place.Code…
	return sdk.DeliveryQuote{Price: 45000, MinDays: 2, MaxDays: 4}, nil
}
```

Владелец заводит способ доставки, выбирает в списке «Обработчик»
`<плагин>/<код>` (`vitams.cdek/door`) и заполняет вкладку «Настройки» —
форма из `Settings`, правила полей те же, что у оплаты («Настройки
способа»). Служба с профилями: ключи вводятся раз у службы («СДЭК»),
профили («до двери», «до пункта») их получают и могут перекрыть своими —
если обработчик службы того же плагина; чужому плагину ключи службы не
передаются. Сменил способ плагин — его прежние настройки стираются.
Покупатель видит способ, только если плагин загружен и все
`Required`-поля заполнены.

**Когда зовётся `Quote`.** На форме оформления и при подтверждении заказа —
после общих границ способа (сумма, вес) и ограничений по плательщику и
зоне: неподходящий способ плагин не тревожит. Все способы плагинов одного
расчёта — параллельно, контекст — **5 с**; не уложились — способ не
показывается. Передавайте `ctx` в `http.NewRequestWithContext`.

**Что приходит** (`DeliveryRequest`): строки корзины с весом и габаритами
единицы (0 — магазин не указал), сумма товаров со скидкой (`Goods`, для
объявленной ценности), общий вес, код типа плательщика, местоположение
(`Place`: название, путь от страны, внешний код ФИАС/КЛАДР/ISO, как его
завёл магазин), индекс, адрес и пункт выдачи — значения полей формы с
ролями «Индекс», «Адрес», «Пункт выдачи» — и настройки способа. Остальные
поля формы не передаются. Запрос — ваша копия, менять его можно.

**Ответ** (`DeliveryQuote`): цена в копейках от 0 до 1 000 000 000, срок в
днях от 0 до 365 (оба 0 — срок из настроек способа). Поверх цены действует
«Бесплатно от» способа: в отгрузке остаются обе — что насчитал обработчик
и что взяли с покупателя. Цены пока нет — `Missing` с текстом для
покупателя («Укажите город»): способ виден с этим текстом вместо цены, сам
не выбирается, оформить заказ с ним нельзя.

**Ошибка, паника, ответ вне границ** (отрицательная цена, срок больше
года) — способ не показывается, текст уходит в журнал магазина. Если
покупатель выбрал именно его — он видит «Служба «СДЭК» сейчас не отвечает
— выбрана другая доставка» и подтверждает заказ заново.

**Кэш.** Ядро помнит ответ 10 минут, ошибку — минуту, для того же
обработчика и того же запроса целиком (способ, настройки, строки с
габаритами, сумма, место, адрес, пункт): пересчёт формы не идёт к
перевозчику каждый раз. Заказ получает цену, которую покупатель видел:
изменилась она к подтверждению — магазин показывает новую и просит
подтвердить ещё раз.

Создать отправление у перевозчика и получить трек-номер — из событий
заказов; выбор пункта выдачи на карте в первую версию не входит: покупатель
вводит пункт в поле с ролью «Пункт выдачи».

## PDF

`api.PDF(sdk.Doc)` собирает документ ядром: шрифт с кириллицей,
подмножество шрифта в файле и извлекаемый текст в каждом плагине писать
незачем. Документ — A4 книжный, поля 15 мм, шрифт ядра (обычный и
полужирный). `Blocks` идут сверху вниз с отступом 2 мм и сами переносятся
на следующую страницу.

- `Block` — абзац (`Text`: длинные строки переносятся по словам, `\n` —
  новая строка) или таблица (`Table` не `nil`). `Size` — кегль, 0 — 10 пт;
  у таблицы — кегль всех ячеек. `Align` — `""` (влево), `center`, `right`.
- `Table` — на всю ширину страницы: `Widths` — доли колонок
  (`{1, 10, 2, 2, 3, 3}`), `Rows` — строки ячеек, `Grid` — рамка вокруг
  каждой ячейки (без неё — подписи «Руководитель ________»). Высота строки
  — по самой длинной ячейке; строка не разрывается, а целиком уходит на
  новую страницу. `Cell.Span` — сколько колонок занимает ячейка, 0 — одну.
- Ошибка — пустые `Widths`, доля не больше нуля, `Span` за край таблицы,
  незнакомый `Align`, больше 100 страниц или больше 1 МиБ текста.
- Картинок (печать, подпись), повтора шапки таблицы на новой странице и
  линий пока нет.

Отдать документ покупателю — из `Start`:
`return sdk.PayStart{File: &sdk.File{Name: "Счёт 123.pdf", Data: data}}, nil`.
Сумма прописью — `sdk.InWords(kopecks)`: 123456 → «Одна тысяча двести
тридцать четыре рубля 56 копеек».

## События заказов

`api.OnOrder(fn)` в `Init` подписывает плагин на события заказов: CRM,
1С, служба доставки узнают о заказе без опроса базы. Нужна группа
`orders:read` в `plugin.json` — без неё плагин не загрузится («OnOrder
требует orders:read»): в событии контакты и состав заказа. Подписка одна
на плагин.

```go
api.OnOrder(func(ctx context.Context, e *sdk.OrderEvent) error {
	if e.Kind != sdk.OrderPaid {
		return nil
	}
	return crm.Send(ctx, e.ID, e.Order) // e.ID — ключ идемпотентности
})
```

- **Виды** (`Kind`): `created` — заказ оформлен; `status` — сменился статус
  (`PrevStatus` → `Status`), в том числе `new → paid` оплатой; `paid` —
  оплачен полностью. Заказ на 0 ₽ даёт `created` и `status → paid`, без
  `paid`. Полная оплата даёт `paid` (ещё со статусом `new`), затем
  `status new → paid`. Виды только добавляются — незнакомый пропускайте.
- **Порядок и повтор.** События идут по возрастанию `ID` в порядке
  фиксации изменений, хотя бы раз, с задержкой до 30 с. Вызовы — по одному:
  следующий только после того, как прошлый вернулся. Ошибка, паника или
  15 с без ответа — то же событие с тем же `ID` позже: через 1 мин, 5 мин,
  15 мин, 1 ч, 3 ч, дальше раз в 6 ч. Обработчик должен выдерживать
  повтор (храните последний обработанный `ID`). Событие, на котором плагин
  ошибается 72 ч, пропускается: иначе один битый заказ навсегда остановил
  бы выгрузку. Пропуск виден владельцу на странице плагина.
- **Истории нет.** Первая подписка начинается с текущих событий.
  «Перечитать» продолжает с того же места. Удалили плагин и поставили снова —
  снова с текущих.
- **Право выключено** владельцем — события ждут, пока его не включат, и
  уходят по порядку. Журнал хранит событие 30 дней и дольше, пока его не
  получили все подписчики.
- **`Order`** — заказ, каким он стал к моменту доставки: `Order.Status`
  бывает новее `Status` события. Строки, поля формы и доставка — снимком
  оформления: каталог и форму потом меняют, событие этого не видит.
  - `Fields` — ответы формы с кодом, подписью, ролью (`name`, `phone`,
    `email`, `location`, `zip`, `address`, `pickup_point`, `comment`,
    `company`, `inn`, `kpp`), сырым значением и текстом. Коды полей у
    каждого магазина свои — смысл поля берите из `Role`. `Values` — те же
    ответы текстом по коду.
  - `Items` — все строки: у строки состава комплекта `ParentID` — строка
    комплекта, суммы у неё нулевые. Деньги — у строк с `ParentID` 0, вес и
    размеры одной единицы (`WeightG`, `LengthMM`…) — у строк без вложенных.
    `ProductExternal`, `OfferExternal` — внешние коды (`Catalog`) на момент
    покупки; у старых заказов пусто.
  - `Delivery` — способ, обработчик (какой выбрал покупатель — снимок
    оформления), цена, склад самовывоза и куда везти по ролям: `Place` (путь
    от страны и внешний код местоположения), `Zip`, `Address`,
    `PickupPoint`. `Settings` — настройки способа сейчас, только если его
    обработчик — ваш (`<плагин>/<код>`) и способ им и остался; иначе `nil`.
  - `Payment` — способ оплаты и его обработчик.
- Даты (`At`, `Order.Created`) — в поясе дат админки. Профиля покупателя
  в событии нет: он под `customers:read`.

## Права к базе

У каждого плагина своя роль Postgres и своя схема. `api.DB()` ходит в базу
этой ролью: ни переключиться на роль магазина, ни выйти из своих прав
плагин не может.

- **Свои таблицы** плагин заводит сам в `Init` (`create table if not exists
  codes …`): они ложатся в его схему, префикс имени плагина в имени
  таблицы больше не нужен. Схема называется `fp_…` (имя видно на странице
  плагина); имя таблицы без схемы ищется сначала в ней, затем в схеме
  магазина.
- **Данные магазина** — только чтение и только по группам прав, которые
  плагин объявил в `plugin.json`:

  ```json
  { "name": "vitams.crm", "title": "…", "description": "…", "version": "1.2.0",
    "access": ["orders:read", "customers:read"] }
  ```

  Нет поля — данных магазина плагин не видит. Группа — не таблица: какие
  таблицы за ней стоят, знает ядро, поэтому смена схемы магазина
  манифесты не ломает. Набор групп закрыт; незнакомая группа — ошибка
  загрузки в магазине и отказ заявки на сайте.

  | Группа | Подпись владельцу | Таблицы (`select`) |
  |---|---|---|
  | `catalog:read` | Читать каталог: товары, предложения, цены, остатки, разделы и свойства | `catalogs`, `categories`, `category_properties`, `products`, `product_categories`, `product_property_values`, `product_relations`, `product_bundle_items`, `offers`, `offer_prices`, `offer_property_values`, `offer_stocks`, `price_types`, `properties`, `property_options`, `stores`, `units`, `images`, `currencies`, `currency_rates` |
  | `orders:read` | Читать заказы: состав, суммы, оплаты, отгрузки и контакты из заказа | представление `plugin_orders` (заказ без ключа доступа к нему), `order_items`, `order_property_values`, `order_status_events`, `order_statuses`, `payments`, `shipments`, `payment_methods`, `delivery_methods`, `payer_types` |
  | `customers:read` | Читать покупателей: имя, почту, телефон и профили — без паролей и входов | представление `plugin_customers`, `customer_profiles`, `customer_profile_values` |
  | `catalog:write` | Менять каталог: товары, предложения, цены и остатки — через магазин, с лимитом товаров | нет: SQL по-прежнему только читает, группа открывает методы `api.Catalog()` (см. «Запись в каталог») |

- **Не выдаётся никогда**: настройки магазина (`settings`), владелец
  (`users`), покупатели с хешами паролей (`customers` — для чтения есть
  `plugin_customers`), сессии и коды входа (`customer_sessions`,
  `customer_auth_challenges`), заказы с ключом доступа (`orders` — есть
  `plugin_orders`), корзины с токенами гостей (`carts`, `cart_items`),
  ключи способов оплаты и доставки (`payment_method_settings`,
  `delivery_method_settings`), служебные таблицы ядра. Справочники
  оформления (местоположения, зоны, тарифы, поля заказа) пока ни в одной
  группе.
- **Записи SQL в данные магазина нет**: запись мимо ядра ломала бы
  оплаченные суммы, остатки и лимит товаров. Каталог плагин меняет
  методами ядра — `api.Catalog()` с группой `catalog:write`.
- **Права включает владелец** на странице плагина в админке. Новый плагин
  — все объявленные группы включены: установка и есть согласие.
  Обновление с новой группой из маркетплейса — включаются группы,
  показанные на карточке перед «Установить»; папкой — новая группа
  выключена, на странице плагина «Плагин просит новое право».
- **Право выключено** — запрос возвращает ошибку «нет права «Читать
  заказы» — включите его на странице плагина»; таблица вне групп — «плагину
  недоступна таблица X». Магазин работает; ошибку плагину стоит показать
  на своей странице.
- Запросы — каждый сам по себе, транзакций в `sdk.DB` нет; соединений у
  плагина — до четырёх. Один запрос — не дольше 15 с, ожидание блокировки
  — 10 с, простаивающая транзакция — 30 с: это настройки роли, свои
  настройки роли (`ALTER ROLE … SET`) сбрасываются при каждом
  «Перечитать». Снять сроки в своём сеансе можно, но сторож ядра раз в
  минуту обрывает сеансы плагина с запросом или транзакцией дольше 30 с и
  с блокировками больше 100.
- Представления, функции и ограничения по таблицам магазина ядро перед
  обновлением своей схемы удаляет — cascade, в пределах схемы плагина — и
  пишет в журнал. Заводите их заново в `Init`
  (`create or replace view …`).
- Удалили папку плагина — роль без входа и без прав на данные магазина,
  схема с таблицами остаётся; вернули папку — плагин видит свои таблицы.
- **Базе магазина не хватает права `CREATEROLE`** (чужой Postgres, старый
  установщик) — плагинам база закрыта: `DB()` отвечает ошибкой, на
  странице «Плагины» — плашка с командой для владельца. Плагин, которому
  база не нужна (плагины оплаты), работает; плагин, создающий таблицы в
  `Init`, остаётся в списке с текстом ошибки.

## Запись в каталог

`api.Catalog()` — товары, предложения, цены и остатки через ядро: лимит
товаров бесплатной версии, пересчёт цен и остатков товара, резервы
заказов и комплекты держит магазин. Нужна группа `catalog:write` в
`plugin.json` и согласие владельца; без них каждый метод возвращает
ошибку: «плагин не просил catalog:write в plugin.json» или «нет права
«Менять каталог» — включите его на странице плагина». Владелец включил или
выключил право — действует со следующего вызова, без «Перечитать».

```go
c := api.Catalog()
id, err := c.SaveProduct(ctx, sdk.CatalogProduct{External: guid, Name: "Футболка",
	Section: "Одежда/Футболки", Unit: "шт", Active: true})
_, err = c.SaveOffer(ctx, sdk.CatalogOffer{Product: guid, External: guid + "#" + feature,
	SKU: "TS-M", Price: 150000, Active: true})
err = c.SetStock(ctx, guid+"#"+feature, 12)
```

- **Внешний код** (GUID 1С, id МойСклад) — обязателен, до 200 знаков, без
  пробелов по краям и не `id:…`. У товара это «Ключ товара» импорта CSV:
  файл и плагин правят одни и те же товары. У предложения — свой код,
  уникальный во всём магазине (у 1С — «товар#характеристика»).
- **Каждый вызов — своя транзакция**; ошибка ничего не меняет. Тот же код
  одновременно из двух мест — ошибка «уже занят», повторите вызов.
- `SaveProduct` создаёт или обновляет товар по коду, пишет все поля.
  **Новый товар сверх лимита бесплатной версии (200) — ошибка** с текстом
  для владельца; правка прежних идёт всегда. Раздел — путём названий через
  `/` (`\/` — косая в названии), недостающие разделы заводятся, сравнение
  без учёта регистра — как у CSV; пусто — без раздела. Единица — код,
  название или сокращение из справочника (`pc`, `Штука`, `шт`); пусто —
  первая (штуки). Каталог — по умолчанию.
- `SaveProduct` предложений не заводит: товар без них виден, но не
  продаётся. Первое `SaveOffer` товара делает предложение основным.
  Пустой артикул — `SKU-<номер>`: без артикула строка CSV не загрузится.
- `SetPrice` — цена и зачёркнутая, копейки. `SetStock` — сколько
  физически лежит на складе по умолчанию; резервы заказов магазин вычтет
  сам, опустить остаток ниже резерва нельзя (ошибка). Магазин без складов
  — остаток прямой. Новое предложение в магазине со складами встаёт на
  склад по умолчанию с нулём.
- **Комплект** — цену, остаток и предложения считает магазин из состава:
  `SaveOffer`, `SetPrice`, `SetStock` для него — ошибка.
- **Удаления нет** — только `Active: false`.
- Перечитанная или удалённая копия плагина в каталог не пишет, откуда бы
  её ни позвали (своя горутина, сохранённый `Catalog`): вызов — ошибка.
- Пока нет: картинок, свойств, типов цен, остатков по складам, кодов
  разделов.

## Платные плагины

Платный плагин продаёт его автор (партнёр), а сайт flycms даёт ключ, выдачу
архива и обновлений. Цена и контакт поддержки — карточка на сайте, а не
`plugin.json`: смена цены не требует новой версии кода.

**Ключ.** Покупатель получает строку `FLP1.…` на домен магазина: плагин,
домен, день выпуска, день конца обновлений. Магазин проверяет подпись
вшитым открытым ключом **без сети** и показывает статус на странице
плагина («Ключ плагина»). Сайт отдаёт архив платного плагина только с
действующим ключом, а после конца срока — только версии, одобренные не
позже этого дня. Бесплатные плагины ключа не требуют.

**`api.License()`** отдаёт плагину его ключ: `Status` (`sdk.LicenseNone`,
`sdk.LicenseValid`, `sdk.LicenseWrongDomain`, `sdk.LicenseBroken`),
`Domain`, `UpdatesUntil` и сам `Key`. Ядро плагин без ключа **не
блокирует** — плагин работает, а что отключить без ключа, решает автор:

```go
if api.License().Status != sdk.LicenseValid {
    // показать «купите ключ», скрыть платную функцию
}
```

Зовите `License()` на каждом запросе, а не один раз в `Init`: ключ
вписывают без перезапуска и «Перечитать». Вне запроса (в `Init`, в
горутине) ядро сверяет домен с последним, на котором магазин открывали.

Метод есть в ядре с версии, где появились платные плагины: укажите в
README плагина минимальную версию магазина, на старом ядре плагин с
`License()` не загрузится.

**Что можно защитить, а что нет.** Плагин — открытые Go-файлы, исходники
ядра есть у покупателей лицензии: проверку ключа можно вырезать, папку —
скопировать. Защищены выдача кода и обновлений, установка в один клик,
поддержка и договор. Самый сильный способ — серверная часть автора: важная
функция плагина обращается к вашему API и передаёт `api.License().Key`, а
сервер сверяет ключ сам. Обфускация не принимается: модератор читает код.

**Модерация платных** дополнительно смотрит: у партнёра указан продавец
и принята оферта платного размещения, есть контакт поддержки, в README
сказано, что плагин делает без ключа, нет обфускации и загрузки кода
извне.

## Контракт только расширяется

Методы `sdk.API` и поля структур sdk добавляются, но не убираются и не
переименовываются: иначе сломались бы чужие плагины. Поэтому функции
обработчиков принимают указатель на структуру — ей можно дорастить поле, а
сигнатуре функции нет. Пустое значение нового поля означает прежнее
поведение. Составные литералы sdk пишите с именами полей
(`sdk.Field{Key: "token"}`, а не `sdk.Field{"token", …}`): позиционный
литерал перестанет собираться, как только в структуре появится поле.

## Проверить у себя

```sh
go build ./...
```

`go.mod` здесь для этого и для подсказок редактора. `go build` проверяет
только, что код компилируется; запреты выше — закрытые пакеты, функции
новее Go 1.22 — видны только при загрузке. Положите папку
плагина в папку плагинов магазина — `/opt/flycms/plugins/` у магазина,
поставленного `install.sh`, — и нажмите «Перечитать» в разделе «Плагины»:
ошибка загрузки видна там же.

## Опубликовать в маркетплейсе

Кабинет партнёра на сайте flycms: регистрация с подтверждением почты и
выбором пространства имён, форма заявки, модерация. Подробный разбор с
примерами — раздел «Документация» на сайте. Заявка — короткое имя (префикс
подставится сам), архив `.tar.gz` или `.zip` с файлами плагина, до пяти
картинок и версия. Что проверяется до модерации:

- в архиве только `*.go` (без `_test.go`), `README.md`, `plugin.json`;
  без подпапок; до 1 МБ;
- имя пакета равно короткому имени плагина, есть `func Init(`;
- версия — semver (`1.2.0`) и больше предыдущей опубликованной;
- картинки — jpeg, png или webp до 2 МБ.

`plugin.json` — карточка плагина, как в [example/plugin.json](example/plugin.json):
`name` (полное, с пространством), `title`, `description`, `version` и
необязательный `access` — группы прав к базе (раздел «Права к базе»). Имя
плагина после первой публикации не меняется: на нём папки в магазинах.

Если SQL плагина рассчитан на новый Postgres, укажите необязательное поле
`postgres` — минимальную мажорную версию сервера базы числом:
`"postgres": 18`. Магазин на сервере старше такой плагин не поставит и не
загрузит, а владелец увидит, какая версия нужна и как обновить Postgres, —
вместо ошибки SQL посреди работы. Без поля плагин должен работать на любом
сервере, на котором работает магазин: сейчас это Postgres 18 и новее.

Модератор читает код и одобряет или возвращает с замечанием — оно видно в
кабинете. Правки опубликованного плагина — та же форма, новая заявка;
карточка показывает последнее одобренное.
